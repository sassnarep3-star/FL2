Requirements register

Decision this page serves: what “done” means before anything is built. Each row is testable against a file in the repo; “Status” is only met where a deliverable here satisfies it today. Rows marked blocked are blocked on a question, and the Depends on column names it.

Reading the statuses

met — a deliverable in this repo satisfies it now
partially-met — mechanism proven, scope incomplete
defined — specified, nothing built yet
blocked — waiting on data or a rights decision

Two statuses are deliberately absent from the vocabulary: almost and in good shape. A requirement is either falsifiable against an artefact or it is recorded as blocked with the dependency named.

All requirements

Source of these requirements: the project brief for this repository (owner’s stated goals), restated into testable form. No external source is claimable for a requirement, so the Source column is suppressed here and appears on every data table instead. Where a requirement depends on a number from the outside world, that number lives in a table that does carry a source link.

Analysis: what the register says about the shape of this project

The centre of gravity is not the model

Of the requirements, the largest group is data plumbing and verification discipline (R-03…R-09, R-39…R-42) — and that is where the blocked items cluster (R-07, R-15, R-27, R-38). A betting model is mostly a data-integrity project with a small model inside it; the register makes that visible instead of hiding it behind “build the model first”.

Nothing in the brief requires a bet to be placed

The brief asks to originate lines, track availability, gate strategies and run a competition. Those are satisfied by R-12…R-24 plus the site and coordination requirements. Wager execution is deliberately out of scope (R-38, Q-15) — it is the part that needs a lawyer and a licence, not a model.

Two requirements are in tension, and that is the point

R-05 (never fill a gap by inference) versus R-12/R-13 (originate a number for every market). Resolution chosen here: refuse to quote where inputs are undefined, and publish the refusal as a first-class result (SIG-22 VETO, SG-12 guard). A line that is “unknown” is more useful than a line that is confidently wrong.

Skill-based selection is a requirement with a formula attached

“Remove luck” (R-18) is not a posture but arithmetic: Wilson bounds, minimum sample floors, deflation by the number of variants tried, walk-forward folds and a bootstrap on the P&L. All of it is implemented in engine/gates.py, so a strategy cannot pass the requirement by narrative.
