Suggestions

Options for the next step — pick one before anything is built

Nothing here is implemented. These are paths with their trade-offs written down so a reviewer can choose, in line with the project rule that a change is not made until a path is selected.

Four paths, each with what it costs and when it is the right choice
#PathWhat it doesTrade-offWhen to pick it
1Extend the capture backwards before fitting anythingCapture Game Books for 2019–2025 so depth-from-playing-time has a multi-season corpus, then fit on it.Costs several hours of CI time and a lot of storage. No model can be fitted until it finishes.Recommended if the goal is a depth feature in a model rather than a verified register.
2Publish the week-10 register and stopShip this section as the reference dataset and let another session build on it.Does not by itself clear R71; it supplies the measurement, not the model.Recommended if the register is the deliverable.
3Cross-check the official snap counts against a third-party countCompare each player's snaps here against a non-official source and publish the disagreement rate.Introduces an unofficial source into a section whose whole premise is official-only.Only if the (Unofficial) caption has to be quantified.
4Derive a 1st/2nd/3rd-string label from snap shares and publish itTurn snap share into an ordinal depth slot per club-position-week.Re-introduces exactly the thing R71 rejects if the threshold is chosen by hand.Only with a pre-registered threshold and the uncertainty published.

Not suggested: deriving depth order from jersey number, experience or salary. That is explicitly rejected in the brief, and the whole point of this section is that playing time is observable while those are not.

FL2 Depth · data captured from official NFL Game Books and hashed. Where the league labels a table (Unofficial), that label is carried on every row that came from it. Rows that could not be parsed from an official source are left blank and listed on Flagged for review — never inferred.
