Machine checks that run before publish

python3 tools/check_site.py

  • every internal href/src resolves to a file in the repo (no broken links)
  • every page appears in the shared navigation and loads the runtime
  • every factual dataset row carries a source or a parent source_url
  • every flag has evidence and a concrete next action; every question has an action, a provisional answer and a priority
  • no placeholder text; .nojekyll and COORDINATION.md present
  • runs python3 -m engine.selftest and cross-checks every number published from computed.js against that fresh output — a hand-edited or stale figure fails the publish gate, so “computed (ours)” cannot quietly drift away from the code

node tools/render_test.js

  • loads every page in a DOM and fails if a table mount renders empty, falls back to “dataset missing”, or produces zero rows
  • fails if a data-stat counter resolves to nothing (a page full of silent gaps)
  • fails if a table offers neither a source link nor an in-table provenance note
  • checks the shared nav, masthead and footer appear on every page

Pre-publish run, 2026-11-14: check_site.py → all checks passed (15 pages, 220 internal links, 19 datasets parsed, 34 factual rows carrying a URL or a resolvable source ID, 18 flags, 22 questions, cross-register ID references resolved, 46 engine assertions, computed figures matched against the fresh run). render_test.js → all pages render, 39 mounts populated, 686 table rows rendered.

The render test needs jsdom (dev-only, not used by the site); the site itself has no dependencies, so a reviewer can skip that check and still get the full picture by opening a page.

What these checks cannot prove

  • that a source is still correct tomorrow — the site is a dated snapshot (FL-015)
  • that the two club/league cross-checks generalise; 30 rows were double-checked, not 276
  • anything about market truth, because no market data is in the repo at all (FL-014)

Which is why the site’s vocabulary separates verified, snippet, computed (ours) and blank + flagged instead of publishing one confident column.

Method used for the data verification

  1. Open the official page; record the title, the week selector state and the capture timestamp.
  2. Transcribe each row as displayed — position, injury text, practice status, designation — without normalising spelling, re-ordering or completing anything.
  3. Re-read the transcribed table against the source for every club in the capture (this is where the vocabulary and blank-designation findings came from).
  4. For the two clubs with a second official feed (league page vs club page), compare player by player, and record agreements and the three wording differences.
  5. Where a field could not be confirmed (e.g. a player on a report but not in the captured roster excerpt), leave the derived value blank and raise a flag rather than guessing the join.
  6. Re-run the numeric claims: every figure published as “computed (ours)” has to appear in a fresh engine.selftest run, which the publish gate checks automatically.
  7. Run the site/data checker and the render test; only then enable Pages.

Ceiling to state plainly: this is single-pass verification by one reader, with a cross-check on a subset. A second independent pass is an open task (Q-19), and until it happens the correct description of the tables is “transcribed from the official page and re-read once”, not “verified twice”.
